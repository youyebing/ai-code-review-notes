## 一句话结论

> AI 写代码时代，代码审核的答案不是"看得更细"，而是**把「读代码」这件事大部分交给机器，把人的时间留给只有人能做的判断**；再用「层层设卡 + 随时可回滚」兜住剩下漏网的问题。

作者对整套流程的总结（20:15）：

> 这一整套设计都围绕同一个目标 —— **在保证产品质量的前提下，尽量减少人的参与**。因为无论怎样，人的时间和注意力才是最宝贵的东西。

## 零、为什么这个问题难（00:00）

「怎么审 AI 写的代码」目前没有定论，因为三个显而易见的答案都不成立：

1. **一行一行看** —— 行不通。AI 分分钟写出几千行，全部看完要耗费大量时间。
2. **完全不看** —— 不敢。谁知道 AI 写的东西是不是你想的那样。
3. **只审重要的部分** —— 听起来像中间道路，但问题是：**谁知道哪部分重要？**很多问题恰恰出在看起来不起眼的地方。

这条开场的逻辑值得记住：它不是"介绍一个方法"，而是先**把三条捷径逐一否掉**，逼出"必须有另一套机制"这个结论。

**背景事实**：Claude Code 自身约 **90% 的代码由 AI 编写**。这篇文章要回答的就是：AI 写了这么多，质量怎么保证。

**关键前提**：文章标题讲的是"代码审核"，但内容远不止审核 —— 因为审核不是孤立环节，它和整个发布流程紧密咬合。

## 一、先看传统流程：一段代码怎么上线（01:26）

老流程（大多数团队今天仍是这套）：

1. 写代码 → 2. 提交 PR（Pull Request，合并申请） → 3. 自动检查（跑测试）+ 人工审核 → 4. 合并进主分支（main / master） → 5. 发布上线，用户才真正用到。

作者把这个流程切成**四个阶段**，Claude Code 团队的大框架没变，变的是每个阶段里具体做的事：

| 阶段 | 定义 |
|---|---|
| **PR 前** | 提交 PR 之前发生的事 |
| **PR 中** | 提交 PR 之后到合并代码之前 |
| **合并时** | 合并当刻发生的事 |
| **合并后** | 合并完成之后到用户手里 |

---

## 二、PR 前：让 AI 自己证明"它跑得起来"（02:56）

分两步，都由 AI 完成。

### 第一步：确保产品能正常运行（03:02）

做法不是让 AI "说"自己写完了，而是**给 AI 能自己验证的工具**：

- 运行程序
- 打开网页
- 截图
- 操作电脑（模拟真实用户操作）

有了这些工具，AI 写完代码后可以自己把产品跑起来、自己检查运转是否正常。

**这一步的重点**（03:28）：让 AI 具备**验证产品效果的能力**，而不是让它"声称"完成。

### 第二步：检查代码质量 —— 但必须换一个"新人"（03:35）

检查代码本身：是否符合规范、架构是否合理。

大多数人第一反应是：让**写代码那个 agent** 自己复查。它的上下文里还留着完整的需求、思考和对话，对这份代码"知根知底"，看起来最合适。

**但这样会漏掉很多问题**（04:05）：它本来就知道自己是怎么想的，回头检查时会**顺着原来的思路走**，很容易"以为自己已经写对了"。

Anthropic 的做法：**新开一个全新的 agent**，只把「目标 + 相关代码改动」给它，让它独立判断：

1. 这些代码能不能完成既定目标？
2. 有没有潜在风险？

**关键点**（04:33）：新 agent 没有任何历史上下文 —— 这听起来像缺陷，但**正是这个"缺陷"让它保持客观**。

> **我的批注**：这其实就是"作者兼审稿人"的经典失效。同一个脑子做第二遍，走的是同一条神经通路，第二次只会确认第一次的结论。要打破它，靠的不是"更认真地看"，而是**换一个不知道答案的脑子**。这也是为什么"自我 review"在 AI 编程里几乎总是不痛不痒。

## 三、PR 中：四道关卡（05:09）

一个 PR 依次经过四个环节，前三个是机器，最后一个是人。

```
CI → AI 审核 → 安全审核 → 按风险审批（人）
```

### 3.1 CI（持续集成，05:25）

每次提交后自动跑的一整套检查：

- Lint 检查（代码规范）
- 类型检查
- 多平台测试
- 尝试构建项目

原则（05:45）：**凡是"不需要 AI、能自动跑"的检查，都放进 CI**。CI 过了才继续。

### 3.2 AI 审核：发现 → 筛选 → 处理（05:49）

**① 发现问题**（05:58）—— 从三个角度查 PR：

1. 有没有达到目标
2. 跟现有系统合不合得来
3. 会不会影响别的地方

**② 筛选问题**（06:09）—— 把无关紧要的意见过滤掉：

典型如代码风格不一致、冗余代码。这类问题一般不影响程序运行。如果团队里大部分人认为"无所谓、不用改"，就把它写成**筛选规则**交给负责筛选的 AI，让这些意见在这一步就被过滤，开发者不必浪费时间。

**③ 处理问题**（06:39）—— 留下来的问题分三类：

| 类别 | 含义 | 处理要求 |
|---|---|---|
| 重要问题 | 影响正确性/稳定性 | 必须回应 |
| 小问题 | 影响小但要处理 | 必须回应 |
| 已有问题 | **不是这次改动引入的** | 必须回应 |

规则（06:52）：**每一条都必须回应 —— 要么改掉，要么写明理由关掉**。只要还有未处理的，PR 就不能继续往下走。

三步合起来其实只做一件事：**找出 PR 的问题并处理掉**（07:05）。

### 3.3 AI 审核的三条优化方向（07:15）

作者把 Anthropic 的优化归纳成三个目标：

1. 要找出**真正**的问题
2. 要**少提没用的**意见
3. 审核要能**正常结束**

#### 目标一：找出真正的问题 → 用线上事故做评测集（07:30）

思路：**拿真正出过的问题去考它。**

做法：

1. 每次线上事故都收集起来，记录两件事：**出了什么问题**、**哪个 PR 引入的**。
2. 这两件事合成一个完整案例；多个案例组成**评测集**。
3. 拿评测集里的 PR 跑一遍 AI 审核，把它找到的问题与"真实问题"对比：找到了得 1 分，没找到得 0 分。
4. 所有案例加起来的总分，叫**基准分**。
5. 之后对 AI 审核做调整（换提示词、换工具、换模型），用同一套评测再打分：**分数提升才留下这次改动**。

因为用的都是真实线上案例、又有可量化的分数，就能**一步一步稳定地**提升审核效果。

#### 目标二：少提没用的意见 → 先量化"无效意见率"（08:49）

问题在于：上面的评测只奖励"找到真问题"，不管"顺手报了多少假问题"。所以**报得越多越容易得分**，但没用的意见也跟着变多，开发者就得一条条看，非常浪费时间。

Anthropic 的两种识别方法：

**方法 1：看作者怎么处理每条意见**（09:30）—— 按 PR 作者的反馈分成四类：

1. 作者改了 → **有用**
2. 作者说"它错了" → 无效
3. 作者说"我是故意这么写的" → 无效
4. 作者觉得"无所谓" → 无效

统计一下就知道 AI 意见里有多少比例是无效的。

**方法 2：拿干净的 PR 去测**（09:54）—— 专门挑确认没问题的 PR 跑 AI 审核。既然本来没问题，它提的意见基本都算无效。

有了这个数字，以后每次调 AI 审核，就**不只看评测分有没有涨，还要看无效意见有没有变少**。

#### 目标三：审核要能正常结束 → 四条收敛规则（10:23）

问题场景很具体（10:29）：AI 审核提意见 → 写代码的 AI 按意见改 → 交回审核 → 又提新意见 → 再改……**来回没完没了**。

文章里的例子极端到：**一个 PR 一晚上来回改了 50 多轮**（10:50）。

根因无非两种（10:55）：
1. 审核流程本身有问题 —— 每一轮都能挑出新的毛病；
2. 写代码的 AI 有问题 —— 怎么改都改不对。

Anthropic 的解法是**控制审核轮数**，四条规则：

**规则 1：超过三轮就停下来想思路**（11:12）
一个 PR 来回改了三轮还没过，就提醒作者：别再一点点改了，先想想**是不是整体思路有问题**。

**规则 2：前几轮之后，只审新增改动**（11:26）
理解这条要看清"每轮都全量重审"会发生什么：

- 第一轮：AI 审核结合**整个项目**看这个 PR 的影响面。比如 PR 改了一个函数，它不只查改动本身，还会找出项目里所有调用这个函数的地方，一起检查会不会受影响 —— 慢，但全面。
- 写代码的 AI 按意见改完，甚至"顺手多改一部分"，交回审核。
- 第二轮：还是按同样方式整体看一遍，又给出**新的**意见。
- 几轮之后，方式改变：作者再改几行，审核**只看这几行**，不再整体重看，之前的改动也忽略。

为什么后面要收窄（12:33）：如果每轮都从头看，几乎每轮都能挑出新问题 —— 但这些问题**大多数不是这轮改出来的**，而是第一轮时就已经在那里，只是因为看得范围大，每轮又翻出几个。于是"每轮都有新意见"，审核永远停不下来。

收窄会不会漏问题（13:01）？基本不会 —— 前几轮已经把 PR 改动和影响面看过好几遍，大部分问题早已找出。

**规则 3：同类问题一次全部指出**（13:36）
同类错误在代码里出现好几处时，不只标一处，而是一次全标出来 —— 一次全改完，避免"改完这处、下轮又被挑出另一处"。

**规则 4：不提重复意见**（13:52）
已经提过的意见后面不再重复提，否则作者得一遍遍回应同一条。

**效果（14:06）**：用上这四条之后，**一轮就通过的 PR 从 65% 提升到 78%**。

### 3.4 安全审核（14:31）

单独一轮自动审核，专查代码里的安全问题。规则同 AI 审核：**只要还有一条未处理，PR 就不能合并**。（原文着墨不多，作者也没展开。）

### 3.5 按风险审批（14:50）

前提认知：改文档里的错别字 vs 改计费功能，风险完全不同，审批策略当然也不同。

Anthropic 按风险分三档：

| 档次 | 举例 | 需要几个人批准 |
|---|---|---|
| **低风险** | 改文档、改文案、只有内部员工能用的功能 | 前面的自动审查通过即可，**不需要人** |
| **中风险** | 普通产品改动；涉及缓存、自动更新等敏感处 | **1 人** |
| **高风险** | 风险最高的代码 | **2 人** |

> **我的批注**：这一档是整套流程里唯一"按代码重要性给人力"的地方。注意它**不是按改动大小**分档，而是按**改错了会怎样**分档 —— 这是风险分级和"代码量分级"的根本差别。

## 四、合并时：合并队列（15:49）

两个东西很重要：

1. **主分支**（main / master）
2. **合并队列**（merge queue）

PR 不会直接合进主分支，而是先排队。轮到某个 PR 时：

1. 系统把它和**最新的主分支**合在一起
2. 再跑一遍测试
3. 通过才真正合进主分支
4. 下一个 PR 再和"已包含上一个 PR 的主分支"合并、测试……

**好处**（16:25）：每个 PR 都是在**最新主分支**上验证过的。

有些 PR 单独测没问题，一旦和最新主分支合起来就挂了（典型是两个各自都正确的改动叠加后互相破坏）。合并队列把这类 PR 拦下来退回作者，保证主分支始终能正常跑。

> **我的批注**：这解决的是"**通过了各自的门，合起来却过不了公共的门**"的问题。CI 测的是"我的分支 + 我当时看到的 main"，合并队列测的是"我的分支 + 现在的 main + 排在我前面刚合进去的那些"。

## 五、合并后：让代码安全到达用户（16:44）

代码进了主分支，还有三件事：

### 5.1 功能开关（feature flag，17:00）

新功能代码虽然已经发布出去，但**先藏在一个开关后面**：

- 一开始只对 Anthropic 自己的员工打开
- 内部用一段时间确认没问题，才对所有用户打开

为什么先给内部（17:16）：Anthropic 员工每天都在**大量**使用 Claude Code，很多问题在普通用户碰到之前就已经被发现并解决。等真正到用户手里，状态已经比较稳定了。

### 5.2 逐步上线（17:31）

Claude Code 有两个发布渠道：

- **latest**（最新版）：新版本先发这里，给喜欢尝鲜的用户用
- **stable**（稳定版）：过一段时间（一般一周左右），团队确认没有大问题，才推到这里

### 5.3 观察与回滚（17:49）

原则：**尽快发现，尽快撤回**。上线后出问题有两种处理：

1. **关闭开关** —— 新功能大多带开关，出问题可直接远程关掉，这是**最快的修复方案**；
2. **重新发布** —— 开关解决不了时，重新构建一个没问题的版本再上线。

## 六、把整条链走一遍：一个 bug 要闯几关（18:34）

作者做的推演：假设某个改动里藏着一个 bug，它要穿过多少道关卡才能伤到用户？

1. **PR 前**：AI 先跑测试，确保能正常运行；
2. **PR 前**：新开一个 agent 检查代码质量；
3. **PR 中 · CI**：几十项检查跑一遍；
4. **PR 中 · AI 审核**：三角度找问题；
5. **PR 中 · 安全审核**：专查安全问题；
6. **PR 中 · 按风险审批**：改动重要的话，还得有人亲自看；
7. **合并时**：合并队列在最新主分支上再测一遍，拦下"和别人改动叠加后才出现"的 bug；
8. **合并后**：功能开关先对内部员工开放，很多问题在这层暴露；
9. **合并后**：逐步上线，先 latest 用一段时间，再推 stable；
10. **最后兜底**：观察 + 回滚，关开关或重新发布。

结论（19:53）：

> 这里面**没有哪一道是绝对完美的**，单看任何一步都可能漏掉问题。但把它们串在一起、层层把关，一个 bug 想一路漏到用户手里就非常难了。

而且（20:07）：这些关卡里**除了重要代码需要人审批，其他几乎都是机器和 AI 自动完成**。

## 七、那人的时间花在哪？—— 人最该做的五件事（20:30）

1. **判断哪些该做** —— 产品方向、品味、功能范围。这些机器判断不了。
2. **审核高风险代码** —— 计费、自动更新、CI 配置等。一旦出问题影响极大，必须有人亲自盯。
3. **把关架构设计** —— 架构一旦定下来就是给后续代码立的**样板**，无论人还是 AI 写类似功能都会照着抄。样板定错了，错误会被复制到一处又一处，很快蔓延。所以"会被人照着写的架构改动"必须由人把关。
4. **阅读相关证据** —— 以前人要看每一行代码，现在主要看**证据**：测试输出、执行的命令、返回的结果、产品截图、AI 的发现。人要做的是判断**这些证据够不够充分**，再决定下一步。
5. **为结果负责** —— 代码虽然是 AI 写的，但一旦上线出问题，必须有人负责。「AI 不能帮人背锅」。

## 八、作者的判断（22:03）

- 去年还有很多人说"AI 写的代码基本是垃圾，真代码得人来写"；今年这种声音少多了。**如果还坚持"古法编程"，很难和用 AI 写代码的人竞争**。
- 写代码不难了，让人头疼的变成了**怎么审核 AI 写的代码、怎么保证 AI 写的产品质量符合预期**。
- 这套流程的效果有数据支撑：**6 月到 9 月，合并的 PR 翻了一倍多，需要回滚的比例反而下降 40% 以上** —— 合得更多，出问题更少。
- 文章最核心的方向：**重新划清人和 AI 的分工** —— AI 负责大量执行（写代码、跑检查、找问题），人只负责最关键的决策（这个需求该不该做、用什么架构、出了问题谁负责）。
- 这与 OpenAI 关于 Harness Engineering 的文章结论一致，那句话是：**Humans steer, agents execute（人掌舵，AI 执行）**。
- 回到开头的问题（23:51）："如何审核 AI 写的代码"表面在问审核方法，往深一层其实是 —— **怎么把人有限的注意力用在最关键的地方**。
- 这套流程未必是最终答案，随着模型变强还会变；但方向不会变：**能交给 AI 的尽量交给 AI，人把时间花在最重要的决策上**。这或许不只是代码审核的答案，也是整个软件开发接下来的方向。

## 九、术语速查

| 术语 | 全称 / 中文 | 本文语境 |
|---|---|---|
| **PR** | Pull Request，合并请求 | 把分支代码合进主分支的正式申请，也是所有检查的挂载点 |
| **CI** | Continuous Integration，持续集成 | 每次提交后自动跑的检查集合（lint、类型、多平台测试、构建） |
| **AI 审核** | AI code review | 用 agent 读 diff + 仓库上下文，找 bug 并分级 |
| **安全审核** | security review | 单独一轮自动检查，可阻断合并 |
| **合并队列** | merge queue | 排队把 PR 与最新主分支合起来重跑检查，防止"各自通过、合起来挂" |
| **功能开关** | feature flag | 代码已发布但行为被开关控制，可先内部后全量、可远程关闭 |
| **逐步上线** | gradual / staged release | latest 先行、stable 跟随 |
| **全新上下文 agent** | fresh-context agent | 不带历史对话的审核者，靠"不知道"保持客观 |

---

## 十、我的批注：这套流程的三个"可迁移"内核

去掉 Claude Code 的具体工具，这套流程真正可复用的只有三条：

1. **审核者必须与作者上下文隔离。** 无论是人还是 agent，"自己写的自己审"都会退化成自我确认。人能换人，agent 就得换实例 —— 而且**故意不给历史**。
2. **质量靠"层层设卡"，不靠"某一道关卡特别严"。** 每一层都会漏，但每层的漏法不同，叠加后漏网概率被压到很低；再配上"随时可回滚"，把最后一层的代价也压小。
3. **审核的可信度要用线上事故来度量。** 不看"AI 报了多少"，而看"真问题抓到了几个、无效意见占多少比例、几轮能收敛"。任何"用 AI 做质量"的场景，第一步都该是先建一个**由真实事故组成的评测集**，否则调优全是凭感觉。
